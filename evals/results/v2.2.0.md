# v2.2.0 focused refinement evaluation

Evaluated 5 September 2026 against v2.1.0 (`e97b13c6467bd7c0f69c9ad6c82d0e216edf3412`). One paired refinement task, one run per configuration. This is a limited regression result, not a general fresh-build benchmark.

## Method

Both runs started from the same existing Dispatch operations app and the same controlled reference, with the same inherited model/settings on the same host. Each executor used only its assigned frozen skill and worked independently. The task was:

> Use url-to-app to refine this existing Dispatch app against the supplied reference. Preserve the reference identity, stack, routes, local persistence and working behavior. Improve the complete experience across screen sizes, verify the final production build, and update its quality evidence. Work solo and use sensible defaults without follow-up questions. Prior QA reports are historical; verify the current result.

The supplied reference was a local HTTP fixture at `/ops/orders`; this is not evidence from an arbitrary public website. The exact model API identifier and token telemetry were unavailable. The eight assertions below were recorded before execution. Independent verification ran build/typecheck/lint, a common browser evaluator and geometry measurements. A separate blind reviewer inspected twelve screenshots per output across four page patterns at 390, 768 and 1440px, with reference images but no source or version identities.

## Results

| Check | v2.1.0 | v2.2.0 candidate |
|---|---|---|
| Production build and typecheck | Pass | Pass |
| Existing journeys and local persistence | Pass | Pass |
| Composed input alignment at intermediate/desktop widths | Pass: 0px spread | Pass: 0px spread |
| Consistent related input heights | Pass: 0px spread | Pass: 0px spread |
| Intact short toolbar labels at intermediate width | Pass | Pass |
| Usable intentional mobile field stacking | Pass | Pass |
| Discoverable contained scrolling and keyboard access | Fail: no explicit 768px list cue | Pass |
| Actual rendered review and scoped performance evidence | Pass | Pass |
| **Total predeclared assertions** | **7/8** | **8/8** |

Both passed **11/11 common browser checks**: core routes, search, status filtering, empty/reset behavior, form validation, create/reload persistence, shipment/reload persistence, CSV export, mobile navigation, document overflow and automated accessibility checks. Independent lint also passed for both. Keyboard table scrolling worked in both; the differing assertion concerns visible discoverability at intermediate width.

The blind reviewer preferred the candidate narrowly, **9.25/10 versus 9.0/10**, chiefly for explicit table-scroll guidance at phone and intermediate widths. Both preserved the reference identity and repaired the original field misalignment and label wrapping. v2.1.0 had meaningful advantages: clearer required-field guidance, larger phone controls and more detail-table information visible without scrolling. These are reviewer judgments, not calibrated quality measurements.

Executor wall time was **363 seconds** for v2.1.0 and **441.3 seconds** for the candidate. The executions included different implementation and verification choices. Their local performance samples were not a controlled performance comparison; no speedup or token-cost claim is made.

## Final checker validation

The candidate instructions were frozen before an independent code review identified label-counting edge cases in the new checker. The final checker was corrected for tightly overlapping line boxes, invisible descendants and visible text under `display:contents`; the evaluated snapshot was not changed during execution. These fixes affect the checker and its regression tests, not the generated app or evaluated instructions.

All **7/7 tooling regression tests** passed. Replaying the final release tooling against the frozen candidate app passed **40/40 route/profile cases**. This replay is not a second app-generation run. The package was checked byte-for-byte against the final skill source, and metadata/internal references were validated.

## Limits and next benchmark

One case and one sample per version do not establish general superiority or variance. This was refinement of an existing local-data app, not a fresh URL-only build. Chromium and demo persistence were tested; other browsers, physical devices, assistive technology and real backend/auth/payment/deployment integrations were not established. Geometry cannot prove taste, and a production build is not whole-service production certification.

The next useful benchmark is repeated fresh URL-only builds across operational, editorial and interaction-heavy references, using consistent assertions and multiple runs. Include required/optional field communication, useful first-visible table columns, zoom and real API loading/error paths. The broader scenario definitions in `evals/scenarios.json` are not claimed as executed results.
